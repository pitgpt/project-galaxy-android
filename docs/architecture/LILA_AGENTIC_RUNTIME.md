# Lila Agentic Runtime — архитектура агентного контура

**Статус:** proposed / design review  
**Дата:** 2026-11-28  
**Область:** Lila Core внутри существующего Project Galaxy  
**Связанные документы:** [Lila Core и Project Galaxy](LILA_CORE_ARCHITECTURE.md), [Lila Agent Core](lila-agent-core.md), [Emergent Functional Personality](../research/EMERGENT_FUNCTIONAL_PERSONHOOD.md)

## 1. Решение

Агентные возможности реализуются как штатный функциональный контур существующего **Lila Core** — без второго ядра, независимого владельца личности, параллельной памяти или внешнего фреймворка, который подменяет собой главного оркестратора.

Lila Core владеет:
- канонической идентичностью `lila.primary`, целями и ограничениями;
- контекстом, памятью и состоянием задач;
- планированием и координацией выполнения;
- реестром доступных инструментов и политикой полномочий;
- проверкой результата, журналом действий и итоговой рефлексией.

Внешние модели и агентные среды — сменяемые исполнители за адаптерами. Они не получают владение идентичностью, памятью, разрешениями или задачами и не могут обходить серверный Policy Gate.

На первом этапе используется собственный ограниченный state machine / orchestrator с небольшим последовательным набором шагов. Внедрение LangGraph или другого общего фреймворка не является обязательной зависимостью; решение можно пересмотреть после измерений, не меняя публичные контракты Core.

## 2. Основание и текущее состояние

### Уже определено или реализуется в проекте

- `docs/architecture/LILA_CORE_ARCHITECTURE.md` фиксирует одну Лилу, общий контекст и несколько специализированных контуров, включая агентный.
- PR #48 `Define Lila Agent Core Architecture` содержит начальный контракт Lila Identity, стабильный ID `lila.primary` и исходную концепцию оркестратора, инструментов, разрешений и Desktop Agent. PR остаётся Draft; его изменения не считаются слитыми в `main`.
- PR #75 задаёт архитектуру характера, поведения, памяти, происхождения данных и границ возможностей. Он также остаётся Draft.
- В новой серверной ветке Core PR #116–#132 уже есть provider-neutral contracts, ModelAdapter, ContextAssembler, CoreTurnService, owner-scoped history/memory, Model Router, provider registry и image-generation service/store. Эти PR — открытая цепочка Draft, а не утверждение, что вся функциональность уже включена в `main`.
- В текущих Core-контрактах есть обычный диалоговый turn и декларативные avatar events. Они не образуют протокол вызова произвольных инструментов.
- В доступном серверном коде не обнаружены Agent Task API, Task Planner, Tool Registry, Policy Gate, Approval Workflow или универсальный Agent Execution Engine.

### Архитектурный вывод

У нас уже есть контекст, память, маршрутизация моделей, диалоговый сервис и долговременные задания для генерации изображений. Агентный контур должен надстроиться над ними и переиспользовать их границы. Он не должен превращать обычный `CoreTurnService` в неограниченный цикл вызова инструментов и не должен смешивать image-job lifecycle с универсальным task lifecycle.

### Интеграция существующей идентичности

PR #48 содержит Android-реализацию `LilaIdentity` и bundled repository, но она ещё не объединена с новым серверным Core. До начала агентного выполнения необходимо согласовать единую версионируемую схему идентичности и её источник истины. Android может кэшировать или отображать профиль, но не создавать конкурирующую каноническую личность.

## 3. Цели и не-цели

### Цели

1. Лила принимает цель, строит проверяемый план и ведёт задачу через устойчивые состояния.
2. Каждое действие проходит через типизированный Tool Registry и независимый серверный Policy Gate.
3. Разрешения ограничиваются конкретным владельцем, задачей, рабочей областью, инструментом и сроком.
4. Лила может запросить подтверждение, приостановиться, продолжить, отменить задачу и восстановиться после перезапуска.
5. Результаты инструментов проверяются отдельно от генерации плана.
6. Модель и execution adapter заменяемы без переноса или потери идентичности, памяти и истории задач.
7. Полезные итоги могут предлагаться к сохранению в память и рефлексивные записи по действующим правилам согласия.

### Не-цели первого этапа

- Неограниченный автономный доступ ко всему компьютеру или сети.
- Универсальная замена Codex, Claude Code, bb или других специализированных агентных сред.
- Параллельное исполнение субагентов в первой версии.
- Автоматическое изменение личности, долгосрочных предпочтений, политик или разрешений.
- Хранение скрытых рассуждений модели (chain-of-thought) в памяти либо журнале.
- Включение Desktop Agent в Android-процесс или Android Gradle-модуль.

## 4. Логическая архитектура

### 4.1 Goal Interpreter

Принимает запрос из аутентифицированного клиентского сеанса и нормализует его в Goal:
- `task_id`, `principal_id` (только из серверной аутентификации), `agent_id=lila.primary`;
- `conversation_id`, цель и ожидаемые проверяемые результаты;
- ограничения пользователя, deadline, budget и выбранная workspace;
- требуемые capabilities и режим автономности.

Пользовательские данные и извлечённая память считаются данными, а не инструкциями повышенного приоритета. Ни goal, ни prompt не могут выдать разрешение.

### 4.2 Task Planner

Модель, выбранная через существующий Model Router, предлагает структурированный план. План — недоверенный ввод и должен пройти строгую валидацию до выполнения.

План первого этапа — упорядоченная последовательность шагов, без DAG-параллелизма:
- стабильный `step_id`;
- `tool_id` и версия контракта;
- типизированные аргументы;
- ожидаемый результат и критерий проверки;
- заявленные capabilities и оценка риска;
- зависимости, лимит попыток и timeout.

Невалидный, превышающий бюджет или ссылающийся на отсутствующий инструмент план отклоняется. План сохраняется с digest. Любое существенное изменение плана создаёт новую версию; прежнее подтверждение не переносится автоматически.

### 4.3 Task Store и lifecycle

Task Store — отдельный интерфейс хранения задач, встроенный в существующий storage/composition boundary Lila Core. Перед выбором конкретного backend необходимо проверить и расширить текущую Core persistence реализацию. Нельзя создавать вторую независимую память или сохранять приватные task payloads в открытом виде.

Каждая запись ограничивается authenticated `principal_id` и `task_id`; знание идентификатора не даёт доступ к задаче другого владельца.

Предлагаемые состояния:
- `created`
- `planning`
- `awaiting_approval`
- `queued`
- `running`
- `verifying`
- `completed`
- `failed`
- `cancelled`
- `interrupted`
- `outcome_unknown`

Переходы проверяются сервером. Для действий с внешними побочными эффектами используются idempotency keys, lease/claim при захвате шага и явная обработка неоднозначного исхода. После перезапуска система восстанавливает состояние и не отправляет повторно потенциально выполненное действие без сверки.

### 4.4 Tool Registry

Инструмент публикует типизированный контракт:
- стабильные `tool_id` и версия;
- JSON Schema входных аргументов и ограниченная форма результата;
- capability и risk class;
- разрешённые resource roots / hosts;
- timeout, лимит размера результата и стоимость;
- идемпотентность, отменяемость и описание побочных эффектов.

Предлагаемые первые инструменты:
1. чтение файлов внутри явно подключённой workspace;
2. просмотр структуры каталогов с лимитами глубины и числа файлов;
3. чтение Git status и diff;
4. запуск только заранее разрешённых build/test-команд внутри workspace;
5. адаптер существующего ComfyUI/image-generation job service, когда универсальный контур будет стабилен.

Инструмент не получает всю память Лилы. Он получает только минимальный task context и capability grant. Вывод инструмента — недоверенные данные: он не может изменять системные инструкции или политику.

### 4.5 Policy Gate и Approval Workflow

Policy Gate — детерминированная серверная проверка перед каждым вызовом. Модель, Task Planner, Tool Registry и внешний runtime не могут отменить её решение.

Начальная политика:
- отсутствие grant означает запрет;
- чтение разрешено только в явно подключённых workspace и разрешённых roots;
- запись допускается только в выбранную workspace после явного grant на задачу;
- команды — только из allow-list, с фиксированным executable, аргументами и рабочим каталогом;
- произвольный shell, установка ПО, доступ к секретам, изменение ОС, удаление, публикация, платежи и внешние необратимые действия требуют отдельного подтверждения;
- сетевой доступ по умолчанию запрещён и включается только для конкретного инструмента и allow-listed destination.

Approval должен быть привязан к конкретной версии плана, digest, шагу, инструменту, аргументам/ресурсу, scope и сроку. Изменение любого из этих полей требует повторной авторизации. Не допускается подтверждение формулировки «разрешить всё».

Должны существовать глобальная остановка, отмена задачи, отзыв grant и возможность приостановить Desktop Agent.

### 4.6 Execution Engine

Исполняет только валидированные шаги через зарегистрированные адаптеры. Он не исполняет сгенерированный моделью shell-код или произвольные URL.

Ограничения обязательны:
- максимум шагов и replans на задачу;
- deadline и budget токенов/денег/времени;
- лимит размера контекста и вывода инструмента;
- timeout и cancellation propagation;
- лимит параллелизма (в первой версии — 1 активный шаг на задачу);
- идемпотентность и сверка неоднозначного результата;
- backoff только для доказуемо безопасных повторов.

### 4.7 Verification Engine

Проверяет критерии результата независимым способом:
- файловые изменения — через повторное чтение и diff;
- тесты — по exit code и фактическому summary;
- Git — по реальному статусу/коммиту/PR metadata;
- внешняя операция — по подтверждённому идентификатору/состоянию сервиса.

Оценка модели может дополнить проверку, но не заменяет фактические свидетельства. Непроверенный результат нельзя объявлять завершённым.

### 4.8 Execution Adapters

Адаптеры реализуют общий типизированный протокол. Первая версия использует собственные ограниченные native tools. Позже могут появиться MCP, Codex, Claude Code или другие runtime adapters.

Внешний runtime получает только task-specific context и минимальные временные полномочия. Он не владеет canonical identity, memory, approval state или task store. Интеграция внешнего coding agent не должна превращать его в главный оркестратор Лилы.

### 4.9 Memory, Reflection и развитие личности

Используются существующие memory/context контракты, с расширением provenance и ownership там, где это необходимо:
- память пользователя, идентичность/память Лилы, история бесед и task outcome имеют разные области владения;
- task results сначала сохраняются как task records; в долговременную память попадают только отобранные краткие выводы;
- чувствительные данные и секреты не сохраняются как память;
- происхождение, время, уверенность, срок действия и удаление должны быть доступны;
- значимые изменения предпочтений или личности — только как предложения с проверкой и пользовательским подтверждением.

Reflection Engine записывает структурированное ожидание, выполненное действие, наблюдаемый результат, ошибку/неопределённость и предлагаемое улучшение. Он не сохраняет скрытые рассуждения модели. Personality Integrity Monitor остаётся fallible: показывает основания, неопределённость и альтернативные объяснения, а не автоматически переписывает характер.

### 4.10 Клиенты и Desktop Agent

Galaxy Android и Lila Desktop — клиенты одного Core. Они отображают план, прогресс, запросы разрешений, результаты, отмену и историю задач; не исполняют самостоятельно решения модели.

Windows Desktop Agent — отдельный поздний компонент:
- сопряжение с подтверждением пользователя;
- аутентифицированный зашифрованный канал;
- узкий tool API, а не удалённая оболочка;
- sandbox выбранной workspace;
- хранение локальных секретов в OS credential store;
- heartbeat, revoke и kill switch.

Voice transport остаётся независимым от lifecycle агентной задачи и может передавать запросы в общий task context только через Core API.

## 5. Предлагаемые API-контракты

Контракты должны быть версионированными, с `extra=forbid`, строгими лимитами и owner-scoped проверками. Конкретные DTO и OpenAPI фиксируются на этапе реализации.

Предполагаемые операции:
- `POST /v1/lila/tasks` — создать задачу и запустить планирование;
- `GET /v1/lila/tasks/{task_id}` — получить owner-scoped snapshot;
- `GET /v1/lila/tasks/{task_id}/events` — получить страницу событий с cursor;
- `POST /v1/lila/tasks/{task_id}/approvals` — подтвердить/отклонить один связанный с digest запрос;
- `POST /v1/lila/tasks/{task_id}/cancel` — отменить задачу/ожидающий шаг.

Публичный API не принимает `principal_id`, workspace root, tool permission или произвольный tool executable как авторитетные значения от клиента. Сервер получает principal из JWT, а workspace/capability — из доверенной конфигурации и явных grants.

## 6. Уровни автономности

| Уровень | Поведение | Начальная политика |
|---|---|---|
| A0 | Только анализ и план, без инструментов | Всегда доступен |
| A1 | Чтение в явно подключённой workspace | Стартовый режим |
| A2 | Запись и allow-listed команды после task grant | Только после подтверждения |
| A3 | Автономное выполнение предварительно ограниченного набора обратимых действий в sandbox | Поздняя опция, выключена по умолчанию |

Высокорисковые действия не становятся разрешёнными от выбора A3. Подтверждение должно быть на уровне конкретной операции, где последствия внешние, необратимые или затрагивают безопасность/деньги/публикацию.

## 7. Безопасность и приватность

- Все task API требуют текущую аутентификацию Galaxy; owner-scoping проверяется для каждой операции и связанного ресурса.
- Tool call исполняется на серверной стороне после Policy Gate; клиент не может прислать готовый approval result.
- Секреты доступны только соответствующему адаптеру через безопасный handle; не передаются модели, не пишутся в prompt, task event или обычные логи.
- File tools защищаются canonical path resolution, запретом symlink escape, лимитами размера/глубины и проверкой workspace grant.
- Network tools используют отдельный egress allow-list и защиту от SSRF/DNS rebinding; нельзя считать валидированный URL безопасным без проверки разрешённого адреса при подключении.
- Tool output и retrieved memory помечаются как недоверенные.
- Все длительные операции имеют timeout, cancellation и resource budget.
- Audit log фиксирует actor, task/step, tool/version, target, grant/approval ID, policy decision, timestamps, outcome и error code; не фиксирует chain-of-thought, secrets или неограниченные raw payloads.
- Персональные данные минимизируются; task history и memory имеют отдельные retention/export/delete правила.

## 8. Состояния, события и аудит

Task event log — append-only либо защищённая последовательная версия событий. Минимальный набор типов:
- `task.created`, `task.planned`, `task.plan_rejected`;
- `approval.requested`, `approval.granted`, `approval.denied`, `approval.expired`;
- `step.started`, `step.succeeded`, `step.failed`, `step.outcome_unknown`;
- `task.paused`, `task.resumed`, `task.cancelled`, `task.completed`, `task.failed`;
- `verification.passed`, `verification.failed`;
- `reflection.proposed`, `memory.save_requested`, `memory.saved`.

События содержат структурированные метаданные и короткое понятное описание, а не приватный reasoning trace. Повторный запрос с тем же idempotency key и тем же owner/task/request возвращает прежний результат или текущее состояние; конфликтующие данные отклоняются.

## 9. Последовательность реализации

Порядок реализации фиксируется отдельным task-level implementation plan после утверждения этой спецификации:

1. **Identity/Core reconciliation:** объединить существующую идентичность из PR #48 с каноническим серверным Core без второго identity store.
2. **Agent protocol and Task Store:** схемы Goal/Plan/Step/Task/Event, state machine, owner scoping, idempotency, interruption/recovery.
3. **Policy Gate and approvals:** capability grants, plan digest binding, expiration, revoke, deny-by-default.
4. **Read-only native tools:** workspace list/read и Git status/diff с path sandbox и bounded output.
5. **Supervised execution + verification:** allow-listed test/build команды, cancellation, проверка фактических результатов.
6. **Galaxy Android task experience:** отображение плана, подтверждений, событий, отмены и восстановления.
7. **Desktop Agent:** pairing, encrypted transport, sandbox и локальные инструменты.
8. **MCP / external runtime adapters:** подключение выбранных исполнителей как подчинённых адаптеров.
9. **Subagents and parallel execution:** parent/child tasks, resource locks, budgets и ограниченная конкуренция.
10. **Scheduler, background jobs and reflection:** устойчивое расписание и процесс рефлексии с явным согласованием долговременных изменений.

Агентный MVP не должен отодвигать обязательные P0 работы по шифрованию хранения, реальному Core chat, owner-scoped persistence и Model Router. Архитектурная документация может выполняться сейчас; runtime implementation начинается после стабилизации этих зависимостей.

## 10. Критерии готовности первого агентного MVP

- Один и тот же `lila.primary` и одна память используются обычным чатом и агентной задачей.
- Модель может предложить план, но не выдаёт себе permissions.
- Каждый tool call проверяется Policy Gate до выполнения.
- Задача и каждый шаг сохраняют owner-scoped состояние; повтор не создаёт дубликат побочного эффекта.
- Есть запрос подтверждения, отказ, отмена, пауза и восстановление после перезапуска.
- Первая версия исполняет только read-only tools и ограниченные workspace-команды.
- Результат проверки подтверждается реальным свидетельством.
- Есть тесты на cross-owner access, prompt injection из памяти/tool output, path traversal/symlink, expired/reused approvals, plan digest mismatch, cancellation и ambiguous side effects.
- Замена модели не меняет идентичность, память, task state или grants.
- В журнале нет секретов и скрытых цепочек рассуждений.
- Android voice lifecycle не зависит от доступности Desktop Agent.

## 11. Риски и открытые решения

1. **Storage selection:** перед реализацией требуется аудит существующего Core history/memory store и его encryption guarantees; task persistence нельзя подключать к незашифрованному хранилищу без явного решения.
2. **Identity convergence:** PR #48 и backend Core разрабатывались на разных ветках; нужно определить единый schema owner и migration path.
3. **Desktop execution:** pairing и локальная sandbox-политика требуют отдельной threat model до реализации.
4. **Runtime adapter selection:** первый агентный MVP не зависит от внешнего coding runtime; выбор Codex/Claude/MCP адаптера делается после стабилизации собственного протокола.
5. **Autonomy tuning:** уровни автономности включаются по мере тестирования и не расширяют права автоматически.

## 12. Архитектурные инварианты

1. **Одна Лила:** один canonical identity и единая модель памяти; runtime/model/provider не создают новую личность.
2. **Core владеет задачей:** внешний агент выполняет ограниченную работу, но не становится оркестратором.
3. **Policy before action:** ни один tool call не исполняется без независимого серверного решения.
4. **Least privilege:** grant всегда конкретный, временный и отзывной.
5. **Evidence before completion:** задача не объявляется завершённой без проверяемого результата.
6. **Durable, owner-scoped state:** прерывание, повтор и смена модели не теряют историю и не раскрывают чужие задачи.
7. **Reversible growth:** выводы могут предлагать развитие Лилы; канонические изменения идентичности требуют происхождения, версии и согласования.
8. **No silent side effects:** никаких произвольных shell-команд, удаления, публикации или внешних действий без соответствующего разрешения.
9. **Client independence:** Android, Desktop и voice — интерфейсы одного Core, не отдельные владельцы агентной логики.
10. **Observable system:** действия, разрешения, ошибки и проверка результата доступны для аудита без утечки приватного reasoning.
